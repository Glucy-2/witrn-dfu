# witrn-dfu

WITRN（维简）USB 电压电流表的 Linux 固件升级工具。

官方升级软件 WITRNUP（`WITRN_UP_V30`）只能在 Windows 上运行。本工具按它的升级协议用 Python 重新实现，只依赖标准库，通过 `/dev/hidraw*` 和设备通信。

## 支持的型号

型号表取自 WITRNUP。设备的 USB ID 决定连接的是哪个型号，固件文件头里的 GUID 决定文件是给哪个型号的。

| A2L | 0716:5050 | 0x08004000 | 109 KiB | `.a2l` | 已用官方固件离线校验 |
| A2C | 0716:5058 | 0x08004000 | 111 KiB | `.a2c` | 已用官方固件离线校验 |

| U3L / U3L Pro | 0716:5054 | 0x08004000 | 1000 KiB | `.u3l` | 已用官方固件离线校验 |

## 安装

```sh
uv tool install ~/Documents/witrn-dfu    # 或仓库的 git 地址；也可以不安装，直接运行 ./witrn_dfu.py
sudo cp 70-witrn.rules /etc/udev/rules.d/
sudo udevadm control --reload && sudo udevadm trigger
```

规则给厂商 ID 0716 的 hidraw 设备加上 `uaccess` 标记，让当前登录用户不用 root 就能访问。

## 使用

```sh
witrn-dfu models                 # 列出支持的型号
witrn-dfu check K2_APP_6.0.k2    # 离线校验固件，显示目标型号和版本
witrn-dfu info                   # 只读：确认处于 DFU 模式，读取序列号、bootloader 和当前版本
witrn-dfu flash K2_APP_6.0.k2    # 擦除、写入、校验、重启
```

- `-d /dev/hidrawN`：同时连接了多个 WITRN 设备时，指定用哪一个。
- `-v`：打印收发的原始 HID 包。

刷写前要让设备进入 DFU 模式，方法见各型号说明书（K2 是按住「-」键上电）。

正常模式和 DFU 模式下 USB ID 相同。设备不在 DFU 模式时不会回应 ping，工具会报错退出，不会进行任何写入。

刷写完成后 bootloader 会重启 MCU，但不会断开 USB（K2 上实测如此），需要拔插一次新固件才会启动。

## 协议

逆向自 WITRNUP。它是 .NET 8 程序，用 .NET Reactor 加了壳；用 NETReactorSlayer 解壳、消除控制流里的恒定判断、解出加密字符串后，协议代码就可以阅读了。

### 传输

HID 中断端点，输入、输出报告都是 64 字节，没有报告 ID。在 hidraw 上写入时要在前面加一个 `0x00`。

| 偏移 | 内容 |
|---|---|
| 0–1 | `FF 55` |
| 2–7 | 由时间戳生成的填充字节；第 4 字节的 bit7 表示「需要回复」 |
| 8 | 命令 |
| 9 | 数据长度 |
| 10–61 | 数据（最多 52 字节） |
| 62 | 第 8–61 字节之和（取低 8 位） |
| 63 | 第 0–61 字节之和（取低 8 位） |

| 命令 | 含义 | 数据 | 回复 |
|---|---|---|---|
| 1 / 2 | NAK / ACK | — | — |
| 3 | ping，用来确认处于 DFU 模式 | — | ACK |
| 4 / 5 | 锁定 / 解锁 flash | — | ACK |
| 8 | 擦除一页 | `u32 地址` | 无 |
| 9 | 写入 | `u32 地址, u8 长度, 数据（≤40 字节）` | 无 |
| 10 | 读取 | `u32 地址, u8 长度（≤52）` | 命令 10，数据从第 10 字节开始 |
| 11 | 批量读取 | `u32 地址, u16 长度（≤4000）` | 若干个命令 11 包，每包 40 字节 |
| 21 | 写一行升级日志 | `u16 1, u16 行号×8, u8 长度, ASCII 文本` | ACK |
| 22 | 清空升级日志 | — | ACK |
| 23 | 重启 | — | ACK |

擦除和写入命令不回复，流控靠 USB 层：HID OUT 中断传输在设备取走上一包之前不会完成。

### 固件文件

整个文件先按 256 字节的替换表逐字节解码，开头是 48 字节文件头：

```
char  magic[7]      "gzutapp"
u16   year; u8 month; u8 day
u8    reserved[9]
GUID  target        目标型号
u32   size          负载长度 = 文件长度 − 48
u32   xor           负载所有字节异或
u32   sum           负载所有字节之和
```

负载就是要写到 APP 起始地址处的内容，第 2048 字节是版本号（`0x60` 表示 6.0）。

### 升级流程

和官方工具一致：

1. ping；读出 1024 字节信息区和 `0x08001400` 处 256 字节的 bootloader 信息。
2. 清空日志；解锁；从 APP 起始地址开始按页擦除，直到覆盖整个文件长度（含 48 字节文件头）；锁定。
3. 解锁；把负载以 40 字节为单位写入；锁定。
4. 按 1 KiB 一块回读并比对。
5. 解锁；向 `APP 起始地址 + 0xC00` 写入 `0xFFFFFFFE`，读回确认；锁定。
6. 重启。

每一步前后写入的升级日志文本和官方相同（包括 `earsing...` 这个拼写）。

K2 的 bootloader 只在两个条件都满足时才跳转到 APP：APP 起始处的初始栈指针位于 `0x2000xxxx`，且 `APP 起始地址 + 0xC00` 处的值不是 `0xFFFFFFFF`。

### 与官方工具的不同

- 擦除页数不超过 APP 区大小。官方工具在文件（含文件头）比 APP 区还大时会陷入死循环，反复擦除 APP 区后面那一页；CC1 3.4 版的「标准_四向」固件就会触发。
- 解锁失败时直接报错退出。官方工具会把擦除当作成功继续往下走。
- 刷写前检查复位向量是否落在 APP 区内，防止地址配错的镜像被写进去。CC1 的固件不以向量表开头，W96D 情况未知，这两款不做这项检查；CL01 没有样本，按其他型号的规律假定要检查，假定错了的结果只是工具拒绝刷写。
- 没有实现官方工具的远程黑名单功能：设备序列号命中服务器下发的列表时，官方工具会擦除型号表里指定的一页（K2 上是 flash 最后一页 `0x080FF800`）并写入 `0x12345678`。
